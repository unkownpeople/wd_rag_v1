# V1 项目现状与准确率判读

> 状态说明：本文记录统一活动集合建立前的 TCS-only 历史快照。当前活动集合、配置和验证结果以 `V1统一集合与第二批修改记录-2026-08-14.md` 为准。

## 1. 结论

对当前项目的理解大体正确，但有四个关键偏差：

1. 项目确实处于年报问答 V1，当前范围应是 TCS 单公司，不做多公司比较。
2. 解析、清洗、切块、向量化和 Qdrant 数量闭环已经完成，但“数据流水线跑通”不等于“端到端问答准确性通过”。
3. Qdrant 的物理集合位于 `xianlian\collection`，运行配置必须把 `QDRANT_PATH` 指向它的父目录 `xianlian`，再用 `QDRANT_COLLECTION` 选择集合。
4. 8 月 14 日最近一次 `16/21` 回答成绩来自三公司实验库，不是当前 TCS 单公司集合的准确率。清理前 `.env` 也错误地指向了该实验库。

因此，当前可以确认的是“单公司数据前置链路闭环”；不能确认的是“当前 TCS 集合端到端准确率已通过”。

## 3. 重叠存储的判断

当前切块保留句子或 token 重叠的方向是合理的。它用于避免一个事实刚好落在切块边界时丢失上下文。

实际数据不是“出现大量异常重复”：

```text
带重叠块：1177
精确内容重复组：41
精确重复额外块：41
含重叠标记的重复组：41
非重叠异常重复组：0
```

但它仍有一个检索层副作用：当前去重键是 `chunk_id`，不是内容哈希或父记录。两个重叠块即使内容高度相似，只要 ID 不同，就可以同时进入候选和最终 Top-K。默认最终 Evidence 只有 5 条时，重复语义可能挤掉另一张表或另一个事实块。

所以，重叠设计本身不是当前低准确率的首要根因；“最终 Evidence 缺少多样性约束”才是需要验证的点。不能通过删除全部重叠文本修复，否则会重新引入边界事实丢失。

## 4. 为什么单公司仍会答错

“单公司”只解决公司隔离，不解决公司内部的证据选择。单个 TCS 年报内仍同时存在：

```text
2022、2023、2024 多个期间
standalone 与 consolidated 多种口径
损益表、资产负债表、现金流量表和附注
表头、目标行、单位、同比列和口径说明
PDF、DOCX、XLSX 多种来源
```

用户只问一家公司时，系统仍要正确完成问题拆分、期间和口径判断、候选召回、证据分配、上下文装配、答案生成和引用校验。任一层丢失目标事实，最终答案都会失败。

### 4.1 运行配置曾经漂移到错误数据库

清理前 `.env` 实际指向：

```text
QDRANT_PATH=F:\新建文件夹\Rag\xianlian_multicompany_eval
QDRANT_COLLECTION=annual_report_multicompany_eval_v1
CHUNK_DIR=...\multicompany_eval_v1_chunks
```

这套库有 1989 点，包含 Apple、Microsoft、TCS。当前指定的 TCS 库有 3173 点。数据库、切块目录和评测题集同时变化时，历史分数不能直接比较。

### 4.2 Planner 仍可能失败并改变整条召回路径

`DeepSeekPlanner.plan()` 没有启用 JSON mode，只从普通文本中用正则截取 JSON，再执行 `json.loads()` 和 Pydantic 校验。最近 21 题记录中有 2 题解析失败，系统退回“原问题直接 Top-5”。

同一批问题因此混合了两条不同路径：

```text
Planner 成功：多 task、多 query、task 内融合
Planner 失败：原问题单次 Top-5
```

这会带来非确定性，也会让组合问题在 fallback 时直接丢失部分事实。

### 4.3 候选很多，但最终仍只保留约 5 条 Evidence

当前每个 task 的每条 query 会取 10 至 20 个候选，task 内再做 RRF；最终选择上限却是：

```python
limit=max(request.top_k, len(task_groups))
```

默认 `top_k=5`。三个 task 即使产生约 90 个原始候选，最终通常仍是 2/2/1 共 5 块。一个精确表格任务若需要表头、目标行和口径说明，只有一块 Evidence 往往不够。

### 4.4 RRF 优先“多次出现”，不保证目标事实优先

task 内融合按每条 query 的排名累加 RRF。概览块若在多条相似 query 中都出现，会获得更高融合分；只在一条精确指标 query 中出现的目标表格行可能被排到后面。

RRF 保证多路排序融合，不保证事实覆盖，也不保证报表口径正确。

### 4.5 重叠块可能消耗有限名额

Dense 和 BM25 的融合结果以及 task 结果都只按 `chunk_id` 去重。带重叠的相邻块或精确重复块有不同 ID 时，仍可能一起占据前 5 名。这不是数据库脏数据，而是排序后的证据多样性问题。

### 4.6 大表展开可能让后续证据全部消失

`assemble_context()` 会把每个首次出现的表格组展开，单表最多使用 6000 字符，总预算为 12000 字符。某块超出剩余预算后当前逻辑直接 `break`，不会继续尝试后面更短的块。

因此，命中的块可能已经进入 `hits`，却没有进入最终上下文和 Evidence。增加 Top-K 也不一定改善这一点。

### 4.7 二次复核可以使原本可用的草稿失效

当前流程先生成草稿，再生成复核稿，只校验复核稿。复核请求失败或复核稿删除引用时，系统不会回退到一个可能已经引用合法的草稿，而是返回不可回答。

最近记录中的引用校验失败属于生成/复核层，不是向量数据库没有命中。

### 4.8 自动检索分数把多个条件用 AND 合并

最近报告中的 `retrieval_coverage=10/21` 同时受数字、概念、family、task 和公司隔离等条件影响。任一字符串条件失败，整题就是 false。

同一报告里：

```text
retrieval_coverage：10/21，47.62%
grounded_answer：16/21，76.19%
answer_completeness：16/21，76.19%
公司隔离：21/21
```

因此，47.62% 不是产品答案准确率；76.19% 更接近那一轮三公司实验的回答表现，但仍不是当前 TCS 集合的成绩。

## 5. 当前准确率应如何表述

当前严谨表述是：

```text
数据闭环：通过，3173 chunks = 3173 points。
异常非重叠重复：0 组。
当前 TCS 单公司端到端准确率：未测定。
历史三公司实验中逐题带公司过滤的回答完整率：16/21。
历史三公司实验公司隔离：21/21。
```

这解释了“为什么不比较公司也会错”：失败并非主要发生在公司过滤，而是发生在同一公司内部的多事实、多口径、多期间证据选择和生成校验。

## 6. 下一轮只应验证的层

应先建立 TCS 单公司固定问题集，并在同一 collection、同一配置、同一模型下记录：

```text

context_fact_recall
draft_citation_valid

```

先确认事实在哪一层消失，再修改对应层。当前没有证据支持重新解析、清洗、切块、向量化或重建活动 Qdrant collection。
