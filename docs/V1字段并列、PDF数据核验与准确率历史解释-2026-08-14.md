# V1 字段并列、PDF 数据核验与准确率历史解释

> 状态说明：本文保留字段并列与历史准确率的审查证据；其中“当前数据库只剩 TCS”属于统一活动集合建立前的快照，当前状态以 `V1统一集合与第二批修改记录-2026-08-14.md` 为准。

## 1. 直接结论

你的记忆是对的：`company_id` 和 `fiscal_year` 本来就应该作为每个向量点的并列 payload 字段存在；多个公司、多个年份也可以同时存入同一集合。V1 的合理边界应是“每次问题只限定一家公司的资料”，不是“整个向量库只能保存一家公司的资料”。

上一轮把“单公司查询”进一步收窄为“只保留 TCS 语料库”，这是范围理解偏差。当前数据库只剩 TCS，是清理后的实际状态，不是 Qdrant 或字段设计的技术限制。本次没有擅自恢复已经删除的三公司实验库。

当前 PDF、切块产物和 Qdrant 的存储闭环基本准确，但“存得对”不等于“问得准”。单公司问答仍会失败，首要原因已经落在检索后的证据选择与上下文装配，而不是公司字段缺失或 PDF 原文错误。

## 2. 字段为什么可以并列

当前代码本身已经证明字段设计支持并列：

- `rag_api/schemas.py` 的请求同时有单值 `company_id` 和 `fiscal_year`。
- `embeddings/contracts.py` 会把这两个字段共同放入显式过滤条件。
- `embeddings/vectorize.py` 会把 `company_id`、`fiscal_year`、`document_id`、`statement_scope` 等共同写入每个 Qdrant payload。
- Qdrant 官方 README 明确说明向量点可以附带 JSON payload，并按关键词、数值范围以及 `must`、`should`、`must_not` 组合过滤。

所以正确结构一直可以是：

```text
同一 collection
├─ Apple / FY2022 / chunk A
├─ Apple / FY2023 / chunk B
├─ Microsoft / FY2023 / chunk C
├─ TCS / FY2022 / chunk D
├─ TCS / FY2023 / chunk E
└─ TCS / FY2024 / chunk F
```

一次只问 TCS 时使用：

```text
must: company_id = tcs
```

若问题明确只问 FY2024，再增加：

```text
must: fiscal_year = 2024
```

这与集合中是否同时存在 Apple、Microsoft 或其他年份没有冲突。

需要区分两个问题：

1. 多公司、多年份并列存储：当前 payload 设计可以做到。
2. 一次查询比较多个公司：当前 HTTP 和检索契约只接受一个标量 `company_id`，尚未实现公司数组、分组召回、跨公司对齐和比较回答。

用户当前没有要求第 2 项。不能因为不做跨公司比较，就删除或否定第 1 项。

还有一个多年份边界：`infer_filters()` 当前只解析一个 `fiscal_year`。若问题同时出现 FY2023 和 FY2024，它可能只取第一个年份并过度过滤。V1 若允许同公司跨年总结，应让 Planner 拆成年份任务，或让年份过滤支持集合，而不能把“库中并列年份”和“单值查询过滤”混为一谈。

## 3. 当前数据库实测状态

```text
Qdrant root：F:\新建文件夹\Rag\xianlian
物理集合目录：F:\新建文件夹\Rag\xianlian\collection\annual_report_tcs_real_multiformat_v2
Collection：annual_report_tcs_real_multiformat_v2
Chunk count：3173
Point count：3173
活动公司：TCS
PDF 年份：2022、2023、2024
```

实际 payload 字段分布为：

| 字段 | 值与点数 |
|---|---|
| `company_id` | `tcs`: 3173 |
| `fiscal_year` | `2022`: 1022；`2023`: 1009；`2024`: 1142 |
| `source_format` | `pdf`: 3055；`xlsx`: 115；`docx`: 3 |

2024 的点数高于 2024 PDF 的 1024 块，是因为跨年度 XLSX/DOCX 研究材料也按 2024 manifest 年份入库；这不影响三份 PDF 各自的年份字段核验，但说明“文档所属财年”和“文档内容覆盖多个年份”仍要区分。

本次审计逐点比较了 Qdrant payload 与正式切块产物，并重新读取三份源 PDF：

| 检查项 | 结果 |
|---|---:|
| 切块数与点数 | 3173 = 3173 |
| 缺失点 / 多余点 | 0 / 0 |
| payload `chunk_text` 与切块原文完全一致 | 3173 / 3173 |
| 公司、年份、页码、格式、哈希等字段不一致 | 0 |
| 三份 PDF 文件哈希与 manifest | 全部一致 |
| PDF 公司、年份元数据错误 | 0 |
| PDF 页码越界 | 0 |
| PDF 切块数 | 3055 |
| PDF 表格切块数 | 531 |

内容忠实度抽查的准确解释是：

- 2851 个含数字的 PDF 块中，2316 个块的全部标准化数字都能在对应 PDF 页文本中找到，占 81.2347%。
- 按块平均数字匹配率为 97.6271%。
- 3055 个 PDF 块的平均词元匹配率为 96.9080%，其中 2524 个块达到至少 95%。

这里测量的是“块中的内容能否回到源页”，不是“源页所有内容是否都已经被切块覆盖”。部分不完全匹配来自页眉、行号、结构化表头或 PDF 文本层抽取差异，因此 81.2347% 不能直接称为问答准确率，也不能直接判定 18.7653% 数据错误。

## 4. 关键 PDF 事实核验

对 TCS 2024 年报做了机器核验和页面渲染目视核验：

| PDF 页 | 原文口径 | 原文事实 | 切块存在 | Qdrant payload 存在 | payload 口径 |
|---|---|---|---:|---:|---|
| 184 | Consolidated Statement of Cash Flows | Cash generated from operations `56,827`；Net cash generated from operating activities `44,338` | 是 | 是 | consolidated |
| 254 | Standalone Statement of Cash Flows | Net cash generated from operating activities `39,142` | 是 | 是 | standalone |

因此这三个典型数字从 PDF 到切块再到 Qdrant 都没有丢失。若最终回答拿不到 `44,338`，不能再归因于“PDF 没解析出这个数字”或“数据库公司年份字段错了”。

## 5. 当前最明确的数据契约缺口

531 个 PDF 表格 payload 全部保存了：

```text
row_matrix
raw_matrix_sha256
```

但 0 个保存完整 `raw_matrix`。

与此同时，`embeddings/retrieve.py::assemble_context()` 只有在 `payload["raw_matrix"]` 存在时才会展开“完整表格上下文”。因此当前真实运行中，这个完整表格展开分支永远不会触发。

这会造成一种典型现象：

```text
源 PDF 有完整表
→ 切块产物也有 raw_matrix
→ 向量 payload 只带单行 row_matrix 和 raw_matrix 哈希
→ 召回时无法恢复完整表头、相邻行和口径上下文
→ 单个事实可能命中，但组合问题缺字段或选错列
```

这不是 Qdrant 损坏，而是向量化写入契约与上下文读取契约不一致。

修复时也不必把完整大表复制到每个行块。更合理的是每个 `table_group_id` 只让一个代表点保存 `raw_matrix`，或把完整矩阵放在可按 `table_group_id` 读取的独立文档存储中；召回到任一行块后再关联展开。这样能修复契约，又不会把当前合理的少量句子重叠扩大成整表重复。

## 6. 为什么单公司仍会答错

“单公司”只排除了 Apple、Microsoft 等其他公司的干扰，TCS 内部仍有大量竞争关系：

- FY2022、FY2023、FY2024。
- consolidated 与 standalone。
- 损益表、资产负债表、现金流量表、附注和经营概览。
- 同一指标的当年列、上年列、同比值、单位和不同披露口径。
- PDF、DOCX、XLSX 多来源。
- 为防止边界丢失而保留的重叠块。

当前主要失败机制如下。

### 6.1 候选多，最终证据仍很少

Planner 的每个 task 会生成多条 query，每条先取 10 至 20 个候选；但 `rag_api/service.py` 最终上限仍是：

```python
limit=max(request.top_k, len(task_groups))
```

默认 `top_k=5`。一个三任务问题即使产生 90 个候选，通常仍只有 5 个 Evidence。需要表头、目标行、单位、口径说明和另一项指标时，5 块很容易不够。

### 6.2 RRF 解决排序融合，不保证事实覆盖

重复出现在多条 query 前列的概览块会得到较高 RRF 分；只在一条精确 query 中出现的目标表格行可能被压后。Qdrant 官方把 RRF 定义为融合策略，也另外提供 MMR 作为结果多样性调节工具，说明“融合”和“覆盖多样性”本来就是不同问题。

### 6.3 重叠设计合理，但会消耗 Top-K

重叠一两句能保护切块边界，当前也没有发现非重叠异常精确重复。问题在于最终只按 `chunk_id` 去重，两个高度相似但 ID 不同的相邻块仍可能一起进入 Top-5，挤掉另一个财务事实。不能简单删除重叠，应在候选选择层做父表、内容或任务覆盖去重。

### 6.4 Planner 和引用校验是独立失败层

历史 21 题记录出现过 2 题 Planner JSON 解析失败，回退为原问题单次 Top-5；还出现复核稿没有合法引用而被拒绝展示。即使向量命中正确，Planner、证据选择、草稿、复核、引用校验任一层失败，最终题目仍会失败。

RAGChecker 的 GitHub README 明确把 Retriever 和 Generator 分开诊断，并分别报告 claim recall、context precision、context utilization、faithfulness 等指标。当前项目把这些层压成一个“准确率”时，很容易把生成失败误判成数据库失败。

## 7. `32/33` 为什么找不到，分数为何看似一路下降

本次检查了当前评测产物和引用任务最近几轮记录，没有找到一份真实执行、可复核的 `32/33` 报告。

实际出现过的是不同性质的数字：

| 记录 | 含义 | 能否直接比较 |
|---|---|---|
| `34/34` | 当时的单元测试通过数 | 不能代表问答正确率 |
| `3/3` | 小规模前端抽测 | 样本太少且不是同一题集 |
| `21/21` | 旧固定题集某轮结果 | 只有在同题集、同库、同模型、同判定器时才可比较 |
| `33 条` | 曾计划扩展后的题目数量 | 不是一次 `32/33` 执行结果，且扩展用例后来被撤回 |
| `16/18` | 三公司前端真实问答验收 | 题集和层次不同 |
| `16/21` | 三公司实验的 grounded / complete | 不是当前 TCS 活动库成绩 |
| `10/21` | 同一轮复合 retrieval coverage | 多条件 AND，不能当作答案准确率 |

所以不存在一条已被证据支持的“32/33 → 21/21 → 16/21”连续下降曲线。题集、数据库、Planner、候选融合、Top-K、评测契约和最终判定含义都变了。

不过，不能把所有下降都解释为评测变严。真实回归也存在：

- 多查询产生更多候选，却仍压缩到约 5 条 Evidence，竞争更强。
- Planner 失败时切换到不同检索路径。
- 表格完整矩阵没有进入 payload，组合事实无法在上下文中恢复。
- 复核稿可能删除引用，使原本有依据的草稿被整体拒绝。
- family、concept 等字符串条件会制造 retrieval 假阴性。

FinQA 的 GitHub 更新记录提供了直接警示：表格行格式错误曾造成 Retriever 成绩虚高，修正后所有基线分数下降；FinQA 同时要求最终做 Retriever 与 Generator 的端到端推理。也就是说，评测和数据格式修正后分数下降，不等于模型突然退化，但也不能因此忽略真实链路缺口。

## 8. 当前准确率应如何表述

截至本次检查，唯一严谨表述是：

```text
当前活动库：TCS，3173 chunks = 3173 points。
PDF / 切块 / payload 的公司、年份、页码和关键数字闭环：通过。
完整表格上下文 payload 契约：未通过，531/531 表格点缺少 raw_matrix。
当前 TCS 活动库端到端答案准确率：未测定。
历史三公司单公司过滤题集：grounded 16/21，complete 16/21，复合 retrieval 10/21。
没有找到真实执行的 32/33 报告。
```

本次没有调用 DeepSeek，没有重新运行 21 题端到端评测，也没有把历史三公司报告冒充为当前 TCS 库成绩。

## 9. 后续收敛顺序

后续不应先重做解析、清洗或 Embedding。应冻结同一批 TCS 单公司问题、同一 collection、同一模型和同一判定器，然后按以下层次记录事实在哪一步消失：

```text
PDF 原文
→ chunk artifact
→ Qdrant payload
→ 每条 query 的候选
→ task 融合候选
→ 最终 selected Evidence
→ assemble_context
→ draft
→ reviewed answer
→ citation validation
```

先修复已经被本次证据确认的 `raw_matrix` 写入/读取契约，再评估 task 覆盖和 Evidence 多样性；不要用增加固定财务关键词、写死公司或测试数字来抬分。

BEIR 的 GitHub 示例使用 nDCG、MAP、Recall、Precision、MRR 等独立检索指标；Ragas 强调客观指标、测试集和反馈闭环。项目后续也应保持“检索指标、答案忠实度、完整性、引用有效性”分层，不再只报一个总准确率。

## 10. GitHub 参考依据

1. [Qdrant README - payload filtering, hybrid fusion and MMR](https://github.com/qdrant/qdrant#features)：payload 可过滤，RRF 是融合策略，MMR 用于相关性与多样性调节。
2. [RAGChecker](https://github.com/amazon-science/RAGChecker)：Retriever 与 Generator 应分层诊断，并使用 claim recall、context precision、context utilization、faithfulness 等指标。
3. [BEIR](https://github.com/beir-cellar/beir)：检索评测应分别报告 nDCG、MAP、Recall、Precision、MRR。
4. [FinQA](https://github.com/czyssrs/FinQA)：财务表格格式错误会造成虚高结果；最终评测要求 Retriever 与 Generator 端到端运行。
5. [TAT-QA](https://github.com/NExTplusplus/TAT-QA)：真实财务报告问答本身就是表格与文本混合问题，单公司也不等于简单检索。
6. [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)：BGE-M3 同时支持 dense、lexical 和 multi-vector；当前项目使用混合检索，但还不能据此声称已经利用全部 BGE-M3 检索能力。
7. [Ragas](https://github.com/explodinggradients/ragas)：强调客观指标、面向生产的测试集和反馈闭环。
