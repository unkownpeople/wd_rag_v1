# V1 统一集合与第二批修改记录

日期：2026-08-14

## 边界确认

V1 允许 Apple、Microsoft、TCS 及多个年份在同一个活动集合中并列保存；一次查询仍只针对一家，不实现跨公司比较。这里的“单公司查询”是查询过滤边界，不是把数据库缩成 TCS-only。

## 第二批代码修改

- `rag_api/service.py`
  - Planner 任务使用轮询候选，Evidence 上限为 `min(max(request.top_k, 2 * task_count), 12)`。
  - 同一完整 `table_group_id`、精确相同的 `chunk_text` 和相同 `chunk_id` 不重复占位，并把命中的任务 ID 合并到保留证据。
  - Planner 失败回退原问题的 Top-10（保留显式公司、年份等过滤条件）。
  - 草稿先做引用校验；复核失败或复核引用不合法时，草稿合法则回退草稿，两者都不合法才拒绝展示。
  - generation metadata 分别保留 draft/review 的 citation check 和最终采用来源。
- `embeddings/retrieve.py`
  - 上下文先加入所有在字符预算内的基础证据，超长证据不会提前 `break` 掉后续短证据。
  - 剩余预算按表格组分配完整矩阵，并设置单表 6000 字符上限。
- `embeddings/contracts.py`
  - 收集所有明确财年；多个财年同时出现时不自动设置单值 `fiscal_year`。
- `rag_api/llm.py`
  - Planner 请求增加 `response_format={"type":"json_object"}`。
  - JSON 解析优先处理完整 JSON，再保留 fenced/包裹文本兼容路径。
- `rag_api/test_api.py`、`embeddings/test_retrieve.py`
  - 增加任务去重、预算公平、复核回退、Planner JSON mode 和多财年过滤回归测试。

## GitHub 参考内容

以下仓库作为本轮实现的外部参考入口，引用的是仓库公开 README/示例所体现的职责划分，不把它们的示例成绩当作本项目成绩：

1. [langchain-ai/rag-from-scratch](https://github.com/langchain-ai/rag-from-scratch)
   - 以“检索结果进入生成上下文”为基本链路，并把检索与生成分开验证。本项目因此把 retrieval-only、上下文组装和最终生成分开记录。
2. [NirDiamant/RAG_Techniques](https://github.com/NirDiamant/RAG_Techniques)
   - 收录 multi-query、结果融合、重排和上下文压缩等 RAG 技术。本项目只取与 V1 风险直接相关的任务级多查询融合、候选去重和预算控制，不引入跨公司比较。
3. [qdrant/qdrant-client](https://github.com/qdrant/qdrant-client)
   - 提供 Qdrant Local、collection、payload 与过滤的 Python 使用示例。本项目沿用 Local `QdrantClient(path=...)`，并把公司/财年过滤作为 payload 契约验证，而不是让 Planner 生成数据库表达式。
4. [explodinggradients/ragas](https://github.com/explodinggradients/ragas)
   - 将 context precision/recall、faithfulness 等 RAG 质量维度分开衡量。本项目因此不把 `3959/3959` 的存储闭环称为问答准确率，仍需在固定题集上单独记录召回、引用、拒答和端到端回答。

## 当前结论

数据和向量存储已恢复为符合 V1 边界的三公司并列活动集合；当前最可能影响单公司准确性的代码问题已完成第二批修改。`3959/3959` 只证明切块与向量点闭环，不能替代固定题集的最终问答评测。下一步验证必须在新活动集合上执行，并把单公司过滤、表格证据、上下文覆盖和最终引用分层记录。
